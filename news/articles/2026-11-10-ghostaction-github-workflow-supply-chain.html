A Workflow Named Security Audit Stole Credentials From Tens of Thousands of GitHub Repos

Socket found a GhostAction variant that added a fake security audit workflow to every repository its two accounts could write to, including Uber's.

Source: Infosecurity Magazine

What happened

Security researchers at Socket have uncovered a software supply chain attack that reached tens of thousands of GitHub repositories, including ones owned by organisations rather than individuals. Uber is named as one of the businesses running compromised packages.

The mechanism was simple. On October 8, 2026, two GitHub accounts, henrywoo and kitao, pushed a malicious GitHub Actions workflow into hundreds of repositories they had permission to modify. The file was named .github/workflows/security-audit.yml, and the commit messages read Add security audit workflow and Update security audit workflow, which is exactly what a routine change looks like.

It performs no security checks. Instead it harvests credentials from the affected repositories and sends them to an external server over plain HTTP.

Socket found the file in tens of thousands of repositories, meaning every repository where either account held write access. Named examples include henrywoo/pyllama and henrywoo/chatllama, two AI projects, a kitao project distributed through both PyPI and crates.io, and uber/athenadriver, where henrywoo holds write access as its original author. Some repositories had been inactive for a decade, which suggests the attackers enumerated everything they could reach rather than picking targets by value.

The campaign is a variation on GhostAction, which GitGuardian documented in September 2025 and which resurfaced in October 2026. This version widens the net. The earlier attacks primarily targeted secrets held in GitHub Actions, such as API keys and access tokens configured for workflows. The new variant also scans repository files and the complete Git history using regular expression patterns, so it finds credentials that were committed by accident and later deleted from the current version. It specifically looks for cloud provider and AI service credentials.

As of October 9, 2026, the workflow was still present on the default branches of the repositories Socket examined, and it had successfully executed, so this was theft rather than an attempted injection. The researchers had not seen malicious package versions published to PyPI or crates.io at that point.

Why this is a GRC story

Write access is a control boundary nobody audits. The attack needed no exploit. It needed a permission that two accounts already held across thousands of repositories, some untouched for years. Access reviews that focus on people and ignore dormant repository permissions leave exactly this door open.

A control can be impersonated. Naming a malicious workflow security-audit.yml is an attack on the reviewer, not the system. It works because security tooling is assumed benign and rarely read. Change review that checks filenames and commit messages rather than diffs is not review.

Deleting a secret does not delete the secret. Scanning full Git history turns every past mistake into a live credential. Rotating on deletion is the only assumption that holds.

The automation layer is production. GitHub Actions holds tokens with real reach. Treating workflow files as configuration rather than privileged code is how a repository-level compromise becomes an organisational one.

What to watch

Watch for the follow on use of the harvested cloud and AI credentials, which Socket had not observed at publication time. That does not mean they are unused. The practical response is to enumerate workflow files across every repository the organisation controls, check who has write access to each, and rotate anything that passed through a workflow in early October.
